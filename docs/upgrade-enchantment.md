# 持续单位升级附魔 · 2.3.1

`CardEffectEnchantCardUpgrade` 复用现有完整列车附魔世界、来源排序、目标收集、
单位升级和预演恢复。每个效果保留主状态与预演目标表；每个目标还保留
`isEnchanted`、待执行动作和实际施加的升级描述，均进入不可变搜索状态。
预演同步逐项覆盖主表键，保留预演表中的历史对象。

原生效果把负攻击从 `attackDamage` 移到 `attackDamageBuff`，再调用单位的直接
升级 API。因此低攻击被减至零后仍能完整恢复，基础攻击和来源卡升级不变。
离开楼层、来源死亡或被封印时撤销，返回范围或解除封印时重新施加。
已销毁、死亡且没有 Undying、预演模式不一致的目标保留原生跳过语义。

三种 BlindingDarkshard 原版单位都是 0 攻／10 血／体积 1，分别向同层敌人
提供 -3／-5／-7 攻击。其 OnSpawn 是自身移到后排，附魔在 AfterSpawnEnchant；
该出生站位也经过实际原生动作对照。原版关联卡是 NonPlayable，场景通过
0 费可打出的控制副本召唤原版单位，三个 CharacterData 定义保持不变。
这些证据不计作三张原版可打出卡的完整验收。

场景包含 12 次操作和 5 次 EndTurn，先在两个敌人上叠加三档减攻，随后封印
与解除、跨层移出移回、分别杀死来源，并验证下一波敌人也能收到与失去附魔。
累计攻击增益依次为 -3、-8、-15、-12、-15、-10、-15、-12、-7，
最后一个来源死亡后新一波恢复至 0；每个来源保留独立升级记录。
独立检查还要求封印确实施加、原版单位未改写、升级不写回来源卡，及搜索键
能够区分仅实际升级描述不同的目标表。

封印在 UI 预演的战后到期时，必须先移除状态并排队通知，再立即刷新附魔。
原版 API 明确执行这一刷新；缺失它会使第二个仍存活目标的预演表不同，
即使实际攻击和主状态都看似正确。

采样启用项目已有的卡牌动画与死亡溶解等待协议：在原生 RunEndMonsterTurn
结束后，等待原有死亡回调入队，再由游戏原有的 ProcessRemovals 清理。
没有该协议，Instant 下有的死亡回调晚于清理，下一回合仍是 InRemoveList，
不能与已完成帧清理的模型边界混用。这是显式隔离采样协议，不能据此宣称
任意玩家会话的销毁时序已经验收。

正式采样约 96.32 秒，原生胜局包含 39 个房间与 9 个列车阶段，四项失败
计数为零，玩家文件未变。完整连续复放／16 路独立分支、12 个录制决策、
16 根候选、128／128 搜索状态和三步计划复放通过；串并行最优一致，候选与
搜索零未支持。旧附魔的 1460 项生命周期、41 项完整队列、32 项共享世界
组件及 15 操作完整链、两份各 115 项的状态触发、受伤加狂热整局定向回归
通过；Probe、ModelChecks、Advisor Release 构建通过，未跑全量回归。

归档为 44,824 字节，SHA256：
`4e7b29cc093caab90d690cbe1efd4e8a6cc8baf177f379959f129960de0bd71e`。

二进制归档与哈希清单位于
`tests/compatibility/game-2.3.1/mechanics/upgrade-enchantment/`，没有 JSON 依赖。
独立入口核对哈希、原生计数、控制结果、完整连续复放／16 路分支和
128 状态串并行搜索：

```powershell
pwsh -NoProfile -File scripts/Check-Game231UpgradeEnchantment.ps1
```

重新采样使用隐藏、静音的隔离 worker：

```powershell
pwsh -NoProfile -File scripts/Run-FullBattleProbe.ps1 -OriginalUpgradeEnchantment -NativeWorker 3 -GameSpeed Instant -BinaryCapture -TimeoutSeconds 180
```

当前证据针对上述原版负攻击附魔。正生命、状态、技能／触发器升级和额外
回调组合，以及 Self 模式、排除克隆、复活、悬停等边界仍需分别原生验收。
升级添加若产生需要立即运行的队列回调，当前明确返回未支持；不会将它
错误地延后到外层队列。原版三个纯数值升级不触发这一拒绝。
这项机制不完成 614 张卡／236 件遗物整体复验，也不改变新增遗物 12/12 的计数。
